# 登录为什么要建一张 session 表？它和 JWT 到底差在哪

> 系列：《我做一个单词后台管理系统时搞懂的事》
> 本文是第 2 篇，聊认证。文章开头提到的疑问，相信很多初学者都有过。

做登录功能的时候，我冒出一个很大的疑惑：

> 为什么要建一张 session 表？里面存的是什么？session 有什么用？
> 还有，session 和 JWT 不是**同样功能**的东西吗？

这篇文章就从这个问题出发，把认证这件事彻底讲清楚。

---

## 一、先搞清楚问题：HTTP 怎么「认出」你

HTTP 是**无状态**的 —— 服务器不记得你是谁。你请求一次、断开，下次再来，服务器完全不认识你。

但登录系统要求：登录一次之后，后续每个请求都知道「你是 admin」。那怎么证明「我是我」？

全世界所有方案，可以归结成**两大门派**：

- **门派 A：服务端 Session（有状态）** —— 把「你是谁」存在服务器这边，给浏览器发一个随机「取件码」。
- **门派 B：JWT（无状态）** —— 把「你是谁」直接打包进 token，服务器看一眼签名就知道，什么都不用存。

---

## 二、门派 A：服务端 Session（我的项目在用）

### 原理

登录时服务器做的事：

1. 生成一串**纯随机**字符串（比如 `x8f2n9...`，不可预测）。
2. 在数据库的 session 表里记一行：「这个码 = 张三，7 天后过期」。
3. 把码发到浏览器的 cookie 里。

下一次请求：

1. 浏览器自动带上 cookie。
2. 服务器拿码去 session 表**查**：有没有这行？过期没？
3. 查到 → 确认你是张三；查不到 → 拒绝。

**关键：那串码本身毫无意义，只是一把钥匙。真正的身份信息存在数据库表里。**

### session 表里到底存了什么

我项目里的表长这样（简化后）：

| token_hash | admin_id | expires_at |
|---|---|---|
| 5f4dcc3b5aa765d6... | 550e8400-e29b-... | 2026-09-02 10:00:00 |

| 字段 | 含义 |
|---|---|
| `token_hash` | 取件码的**哈希**（存哈希不存原文，原因见下） |
| `admin_id` | 这是**谁** |
| `expires_at` | 什么时候**作废** |

**这一行，就是一个「session」。** 定义 = 一串随机凭证 + 它属于谁 + 它什么时候死。

### 为什么存哈希而不是原文？

防御纵深。如果数据库被拖库，黑客拿到的是 token 的 SHA-256 哈希。而 token 本身是 32 字节随机数，哈希不可逆、又没法暴力猜 —— 等于拿到一堆废纸，伪造不了任何会话。cookie 里存原文（浏览器需要），数据库只存哈希。

### 完整的三步验证代码

```ts
export async function getCurrentAdmin() {
  const token = (await cookies()).get(SESSION_COOKIE)?.value; // ① 从 cookie 拿取件码
  if (!token) return null;

  const [row] = await db
    .select({ id: adminUsers.id, name: adminUsers.name, role: adminUsers.role })
    .from(adminSessions)
    .innerJoin(adminUsers, eq(adminSessions.adminId, adminUsers.id)) // JOIN 出用户资料
    .where(
      and(
        eq(adminSessions.tokenHash, hashToken(token)), // ② 哈希后去表里找
        gt(adminSessions.expiresAt, new Date())        // ③ 确认没过期
      )
    )
    .limit(1);

  return row ?? null;
}
```

三步：**取码 → 对表 → 查过期**。这就是服务端 session 的完整生命周期。

### 登出 = 立刻失效

服务端 session 最大的好处：想踢人下线，**删掉表里那行就行**，立刻生效。

```ts
await db.delete(adminSessions).where(eq(adminSessions.tokenHash, hashToken(token)));
cookieStore.delete(SESSION_COOKIE);
```

## 三、门派 B：JWT（无状态）

JWT（JSON Web Token）的思路完全不同：**把身份信息直接放进 token 里，服务器不用存任何东西。**

### 一个比喻：签名欠条

JWT 就像一张**签名欠条**：

> 「我，服务器，在此证明 token 里写的这个人确实登录过。」—— 用服务器密钥盖了章。

任何人拿欠条来，服务器验一下章是真的，就认。因为**章没法伪造**，所以内容可以明文写在欠条上 —— 就算别人看到了内容也改不了（一改签名就失效）。

JWT 的结构是「三段式」：`头部.载荷.签名`

```
eyJhbGciOiJIUzI1NiJ9.eyJhZG1pbklkIjoiNTUwZS4uLiIsImV4cCI6MTc2Nz...9kQ1
     └头部(算法)      └载荷(你是谁,什么时候过期)        └签名(盖章)
```

### 验证：不用查库

服务器拿到 JWT，用密钥验一下签名：

- 签名对得上 → 内容没被改过 → 直接读出 `adminId`
- **全程不查数据库**。这就是无状态的含义。

登录后每次请求，`getUser()` 解一下 token 就知道是谁。

## 四、Session vs JWT：一张表看清

**先回答最初的问题：它们解决同一个问题（HTTP 认出你），但机制完全相反。**

| | 服务端 Session | JWT |
|---|---|---|
| 身份信息存在哪 | **服务器数据库** | **token 自己肚子里** |
| token 里有什么 | 无意义随机字符 | 明文 `{adminId, 过期}` + 签名 |
| 每次请求验证 | **查数据库** | **算签名**（不查库） |
| 想立刻踢人下线 | 删行 → 立刻生效 ✅ | 等自然过期 ❌ |
| 多服务器扩展 | 要共享 session 存储，麻烦 | 任何服务器验签即可，天然适合 ✅ |
| token 体积 | 很小 | 较大（几百字节起） |

核心一句话：

> **Session 是有状态的 —— 服务器记住了你；JWT 是无状态的 —— 服务器不用记，token 自己证明自己。**

比喻再收尾一次：

- **Session 的 token** = 超市储物柜**小票**。小票上啥信息没有，就是个号码。柜员得去**翻他的本子**（数据库）才知道 78 号柜里存了你的包。
- **JWT** = **签名欠条**。内容写在明面上、盖了章，验章即认，不用翻本子。

---

## 五、什么时候用哪个？

| 你的诉求 | 推荐 |
|---|---|
| 要能**立刻**踢人下线 / 改权限立刻生效 | Session（或 JWT + 撤销名单） |
| 多台服务器横向扩展 | JWT |
| 学习原理、看得到底在干嘛 | Session |
| 不想维护会话存储 | JWT |

**而且它们并不互斥** —— 很多系统混着用：主 token 用 JWT，再配一张 session 表当「撤销名单」，记录哪些 JWT 已被强制下线，用查库弥补 JWT「踢不了人」的短板。看到这你就能看懂那些「又用 JWT 又建表」的系统了。

> 补充：我们上一篇说的 Supabase Auth 返回的登录凭证就是 JWT —— 所以接云服务时你拿到的往往是无状态方案。

---

## 小结

1. **session 表存什么**：随机凭证 + 属于谁 + 过期时间，三列就够。
2. **session 有什么用**：让无状态的 HTTP 认得出「带这把钥匙的人是谁」，并能立刻作废。
3. **session 和 JWT 是不是重复**：解决的问题相同，**机制相反** —— 一个有状态（可踢人、要查库），一个无状态（不查库、踢不了人）。选哪个，取决于你在意「可控性」还是「可扩展性」。
